attention-track-eye — Work Process

A 3-phase webcam gaze-estimation pipeline: MediaPipe face mesh → eye + head-pose feature extraction → calibrated feature→screen mapping → fixation-aware gaze-density heatmap. Pupil/iris and facial features are inputs to a calibrated model — pupil position alone is never treated as the direct gaze direction.

gaze_core.py + phase1 / phase2 / phase3

1 · System overview architecture

Webcam frames flow through three phases. Each phase is a separate script; gaze_core.py holds the shared configuration, feature definitions, confidence model, mapping models and heatmap used by all of them.

INPUT

Webcam Frame

cv2.VideoCapture grabs 1280×720 frames, mirrored horizontally by default.

→
PHASE 1

Eye + Head-Pose Features

FaceMesh 478 landmarks → eye warp 200×100 → pupil/iris + solvePnP head pose → 11-channel feature vector → confidence-weighted eye fusion.

→
PHASE 2

Calibration & Mapping

5/9/13-point multi-sample calibration → affine | polynomial | MLP → outlier rejection → EMA → 1920×1080 pixels.

→
PHASE 3

Gaze-Density Heatmap

I-DT/I-VT fixation detection → confidence- & fixation-weighted accumulation → exp(−Δt/τ) decay → Gaussian blur → TURBO render.

Files & responsibilities

  • gaze_core.py (2054 lines) — config, features, confidence, head pose, fusion, calibration, mapping models, heatmap.
  • phase1_eye_tracking.py (210) — live eye / head-pose feature view.
  • phase2_coordinate_mapping.py (890) — calibration, mapping, validation, evaluation reports.
  • phase3_attention_heatmap.py (713) — fixation detection, accumulation, decay, rendering, export.
  • test_gaze_pipeline.py (829) — 52 offline tests, no webcam needed.

2 · Phase 1 — Eye & head-pose feature extraction phase1_eye_tracking.py

Turn a webcam frame into a normalized 11-channel feature vector plus five separate confidence components. Pupil/iris localization, per-eye gaze input and screen gaze are kept conceptually distinct: screen coordinates only exist after Phase 2 calibration.

What it does

  • Runs MediaPipe FaceMesh (468 + iris landmarks, 478 total) per frame.
  • Crops both eyes into fixed 200×100 rectangles via perspective warp.
  • Finds the pupil inside each crop (3 detection modes) and keeps the iris landmark as an independent signal.
  • Estimates head pose (yaw/pitch/roll) with cv2.solvePnP from 6 stable landmarks against a 3D head model (~60° FOV pinhole camera).
  • Fuses both eyes by quality weight — never a plain average.

gaze_core.py → EyeTracker, estimate_head_pose, build_feature_vector, fuse_eye_gazes

Pupil modes (--pupil / key i)

  • hybrid (default) — image detection if confidence ≥ 0.6, else iris landmark.
  • iris — trust MediaPipe iris centre (landmark 468/473) first.
  • image — Otsu threshold + contour circle first, iris as fallback.

Feature vector (11 channels)

  • left/right_eye_x,y — pupil offset vs aperture centre, normalized by aperture size.
  • left/right_iris_x,y — pupil position inside the 200×100 crop (0…1); imputed to 0.5 if an eye is missing.
  • head_yaw, head_pitch, head_roll — degrees ÷ 30 so all channels share a scale.

Head pose — what it does and does not fix

  • Reprojection error, angular plausibility (±60/50/45°) and frame-to-frame stability are combined into a head-pose confidence.
  • Head pose is a feature of the mapping model, so orientation-related gaze error is compensated for in calibration, not removed by assumption.
  • Head-pose compensation reduces but does not eliminate error from head movement; measure it with the per-head-pose validation buckets.

estimate_head_pose() → HeadPose(yaw, pitch, roll, confidence, reprojection_error)

Eye quality → fusion weight

Each eye gets a quality score in [0,1] used as its fusion weight:

quality = 0.35·pupil_conf + 0.15·contour_quality + 0.15·geometry + 0.15·contrast + 0.10·temporal + 0.10·visibility, scaled by clip(head_pose_conf, 0.4, 1).

Missing pupil, degenerate aperture or an all-poor pair yields None instead of a plausible-looking point, so the sample can be rejected downstream.

3 · Phase 2 — Calibration & gaze mapping phase2_coordinate_mapping.py

Map the feature vector to absolute pixels on a virtual 1920×1080 screen, with outlier rejection and configurable EMA smoothing — then measure the result in validation mode.

Two mapping paths

  • Raw (no calibration): x = (0.5 + (gx−base_x)·gain)·W — gain 3.0, baseline auto-centred over 45 warmup frames. Transparent baseline, not a model.
  • Calibrated: a mapping model is fitted on Features → Known Screen Coordinate samples and predicts from the full 11-channel vector.
  • Both clamp to screen bounds, then apply new = α·x + (1−α)·old with ema_alpha (default 0.3).

gaze_core.py → ScreenMapper, build_mapping_model

Mapping models (--mapping)

  • affine — X = a₁f₁+…+b₁, least squares baseline (default).
  • polynomial — second-order terms x, y, x², y², xy, … on standardized features, light ridge (1e-2), including head-pose interactions.
  • mlp — Dense(16) → tanh → Dense(2) in plain NumPy; optional, never mandatory.
  • Complexity is never presumed better: --compare-models measures all three on the same validation features.

AffineModel / PolynomialModel / MLPModel

Outlier rejection

  • Confidence < confidence_threshold (0.5) → rejected.
  • Missing feature vector while calibrated → rejected.
  • Prediction outside the screen by > 10 % margin → rejected.
  • Jump > outlier_max_jump_px (default 1.5 × screen diagonal — beyond any reachable on-screen jump) → rejected, so real saccades are never rejected for being fast. Optional speed limit is off by default.
  • Every rejection is counted in ScreenMapper.stats → valid sample rate.

ScreenMapper.map() · stats: accepted / rejected_low_confidence / rejected_off_screen / rejected_jump / rejected_missing_features

4 · Phase 3 — Fixation-aware gaze-density heatmap phase3_attention_heatmap.py

Mapped gaze samples are classified as fixation / saccade / invalid, accumulated with confidence and fixation-duration weights, decayed in time (not per frame), blurred, normalized, gamma-corrected and colourized. The baseline output is a gaze-density heatmap; it becomes a visual-attention estimation component only because fixation duration and confidence are folded into the weights.

Fixation / saccade detection

  • I-DT (default): a window stays a fixation while dispersion ≤ 45 px and duration ≥ 100 ms.
  • I-VT (--fixation-method ivt): velocity < 1 px/ms (1000 px/s) is stable, above it is movement.
  • Labels: fixation, saccade, invalid (missing or below the confidence gate).
  • Each fixation stores start, end, duration, centroid, confidence, dispersion and sample count; saccades store amplitude and peak velocity.

EventDetector — fixation_events.json export on save / exit

Accumulation math

  • Grid cell = 4 px → matrix shape 480 × 270 (1920/4 × 1080/4).
  • add(x, y, t): grid += confidence × fixation_weight — fixation weight is Δt × 10/s (saccades × 0.1), so a 700 ms stable fixation contributes ≈ 7.0 vs ≈ 0.1 for one noisy sample.
  • Samples below heatmap_min_confidence (0.35) are discarded, not down-weighted equally.
  • Calibration and pause ([p]) suppress accumulation so dwell frames don't pollute the map.

gaze_core.py → AttentionHeatmap.add()

Decay, blur and rendering

  • Time-based decay: grid *= exp(−Δt/τ), τ = 5 s — identical behaviour at 30 fps and 60 fps (frame-based ×0.997 is gone).
  • Blur units: σ = 45 screen px → σ_cells = 45/4 = 11.25 → kernel 2·round(3·11.25)+1 = 69. The HUD shows both units.
  • Render: normalize by peak → pow(n, γ=0.75) → TURBO colormap → alpha blend (0.7) over the camera frame or a dark canvas.

5 · Confidence model 5 separate components

There is no single generic confidence number. Five interpretable components are computed separately and combined with explicit, configurable weights.

ComponentMeaningHow it is computedWeight
pupil Reliability of pupil/iris localization Quality-weighted pupil detection confidence of the visible eyes 0.30
landmark Stability / reliability of facial landmarks Face size (inter-ocular distance vs frame) + frame-to-frame landmark stability 0.20
head_pose Stability and plausibility of head pose 0.5·reprojection term + 0.3·angular plausibility + 0.2·temporal stability 0.15
gaze Reliability of the combined gaze estimate 0.45·pupil + 0.25·landmark + 0.20·head pose + 0.10·two-eye completeness 0.25
temporal Consistency with recent gaze estimates Allowed displacement grows with Δt (0.3 + 4·Δt) so real saccades are not punished 0.10

Combination

combined = Σ(component × weight) / Σ(weights) — weights live in GazeConfig.confidence_weights. The full breakdown (pup / lm / hp / gz / tmp) is printed in every HUD, so a low score can always be traced to a cause instead of guessed at.

Where confidence is enforced

  • Calibration samples below 0.35 are rejected (and reset stabilization).
  • Screen mapping rejects samples below confidence_threshold (0.5).
  • Heatmap accumulation rejects samples below heatmap_min_confidence (0.35).
  • Eye fusion rejects when summed eye quality < 0.12.

6 · Calibration procedure 5 / 9 / 13 points

Calibration collects Features → Known Screen Coordinate pairs — not a single frame per point. The 5-point layout stays available as a lightweight mode.

Layouts

  • 5 points — 4 corners (8 %/92 %) + centre: lightweight legacy mode.
  • 9 points (default) — 3×3 grid at 10/50/90 %, centre visited first.
  • 13 points — the 9-point grid plus four inner-diamond targets for interior coverage.

--points · GazeConfig.calibration_points

Per-target parameters

  • calibration_stabilize_frames = 12 — dwell before sampling starts.
  • calibration_samples_per_point = 20 — accepted frames per target.
  • calibration_min_confidence = 0.35 — low-confidence frames rejected.
  • calibration_outlier_z = 3.0 — MAD-based z-score per target.
  1. Display the target — a ring with a progress arc appears at the known screen coordinate.
  2. Wait for stabilization — 12 consecutive valid frames are required before any sample is taken; a rejected frame resets the counter.
  3. Collect multiple valid frames — 20 samples per target (configurable), each with its feature vector and confidence.
  4. Reject low-confidence samples — below 0.35 the frame never enters the dataset.
  5. Reject extreme outliers — MAD-based z-score (3.0) removes contaminated frames per target.
  6. Compute a robust median — a median feature vector per target is stored as the representative sample.
  7. Store the dataset — every accepted pair plus the model parameters are saved to calibration.npz (screen size checked on reload).

SPACE performs a manual capture of the current target using whatever has been collected; [r] resets everything. A fit is refused if there are fewer than 4 samples or if the feature spread is below min_calibration_span (0.25) — degenerate data cannot produce a mapping.

7 · Validation methodology screen-space error

Guided validation against known screen targets. The pipeline's accuracy is whatever this mode measures on your setup — nothing in the codebase asserts otherwise.

  1. Show known targets — a 5 / 9 / 13-point layout (defaults to the calibration layout).
  2. Stabilize, then sample — after a dwell period, predictions are collected (--validation-samples, default 15 per target); low-confidence frames are logged as invalid instead of recorded.
  3. Per-record error — error_px = √((predicted_x − target_x)² + (predicted_y − target_y)²).
  4. Aggregate — mean, median, standard deviation, 95th percentile and maximum, overall, per target, and per head-pose condition (neutral ≤ 8°, slight ≤ 20°, moderate above).
  5. Export — evaluation_report.json + .csv, plus evaluation_report_pairs.npz (raw targets/predictions) for offline analysis.

Comparisons supported

  • Raw / baseline vs calibrated — validate once without a calibration file, once after calibrating, then compare the two reports.
  • Affine vs polynomial vs MLP — --compare-models refits all three on the stored calibration samples and evaluates each on the identical validation features.

No winner is declared without measured data; the report simply records what each model did.

Angular error (optional)

When the physical geometry is known — --screen-width-cm and --camera-distance-cm — the mean pixel error is converted to degrees:

theta = atan(error_px * cm_per_px / distance_cm)

If either value is missing, angular error is not reported; it is never computed from guessed numbers.

Head-pose conditions

Errors are bucketed by measured yaw/pitch (neutral / slight / moderate / unknown), so the effect of head-pose compensation can be measured rather than assumed. Report these buckets before and after enabling head-pose features to quantify any benefit.

10 · Limitations read this before trusting a number

The pipeline's accuracy depends on conditions the algorithm does not control. Research-grade accuracy must never be claimed without measured validation on the target setup.

Camera position

A webcam below the screen forces an unfavorable gaze/camera geometry; the ~60° FOV pinhole model is an approximation, not a calibrated intrinsics estimate.

Lighting

Low light, backlighting and glare degrade pupil detection and landmark stability; infrared would be more robust than visible light.

Glasses / reflections

Specular reflections can be mistaken for the pupil and occlude the iris; the contour-quality term mitigates but does not remove this.

Eye shape & anatomy

Eyelid shape, monolid eyes, makeup, eyelashes and contact lenses change the eye aperture and the apparent pupil position.

Head movement

Head-pose compensation reduces but does not eliminate error from head movement and camera-relative orientation.

Face occlusion

Hands, hair or objects over the face drop landmark confidence and can invalidate frames entirely.

Webcam resolution

A 200×100 crop carved from a 720p frame limits pupil precision; low frame rates reduce fixation and temporal-confidence resolution.

Monitor geometry

Second monitors, unusual scaling or a preview that is not the assumed virtual screen break the pixel mapping; angular error needs real physical geometry.

Calibration quality

Sparse, rushed or low-confidence calibration produces an inaccurate mapping regardless of the model chosen.

Individual variation

All thresholds (dispersion, confidence gates, quality weights) are heuristics tuned on generic data and may need re-tuning per person.

12 · Research methodology notes integrity

How to make an accuracy claim

  • Run validation on the target hardware — the offline test suite checks algorithm behaviour on synthetic data, not accuracy.
  • Report the configuration with the number: model, calibration layout, samples per point and the rejection counts are all written into the JSON report.
  • Quote valid sample rate next to error: a low error on 5 % of frames is not a result.

Comparing fairly

  • Evaluate affine / polynomial / MLP on the same validation features (--compare-models).
  • Compare raw vs calibrated by running validation twice, not by intuition.
  • A more complex model is never presumed better — measured error decides.

Measuring head-pose compensation

  • Errors are bucketed by measured yaw/pitch (neutral / slight / moderate).
  • Run the same session with and without head-pose channels to quantify the effect rather than assuming it.

Terminology discipline

  • Baseline output = gaze-density heatmap.
  • Visual attention estimation only when fixation duration + confidence weighting are actually applied.
  • "Pupil/iris and facial features are inputs to a calibrated gaze-estimation model" — never "the pupil position shows where the user is looking".

What has been verified here

  • 52 offline tests pass (head pose recovery, fusion, calibration, all three mapping models, fixation detection, time-based decay, σ unit conversion, reports, and a synthetic end-to-end Phase 1 run).
  • All three CLIs start and parse arguments; pyflakes is clean.
  • Not verified here: live webcam capture, real-face pupil behaviour and live on-screen sessions — no camera was available in the development environment.

What is deliberately not claimed

  • No "research-grade accuracy" — no measured before/after experiment is shipped with the repository.
  • No elimination of head-movement, lighting or anatomy effects — only mitigation.
  • No validation of the Python pipeline by the JavaScript demo.
